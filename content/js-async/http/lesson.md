# HTTP

Браузер и сервер разговаривают по протоколу HTTP. Разговор всегда устроен одинаково: **браузер отправляет запрос, сервер возвращает ответ**. Сам сервер ничего не присылает, пока его не спросили.

Знание HTTP нужно по обе стороны: в JavaScript ты составляешь запросы, в PHP — разбираешь их и составляешь ответы.

## Запрос

```text
POST /api/orders?source=web HTTP/1.1
Host: zerno.example
Content-Type: application/json
Cookie: session=abc123

{"product": 4, "qty": 2}
```

| Часть | Что это |
|---|---|
| Метод | `POST` — что сделать |
| Путь и параметры | `/api/orders?source=web` — с чем |
| Заголовки | Служебные сведения: тип данных, cookies, язык |
| Тело | Сами данные. У `GET` тела нет |

### Методы

| Метод | Смысл | Тело | Пример |
|---|---|---|---|
| `GET` | Получить | Нет | Список товаров, страница |
| `POST` | Создать или выполнить действие | Есть | Новый заказ, вход |
| `PUT` | Заменить целиком | Есть | Обновить профиль |
| `PATCH` | Изменить часть | Есть | Поменять статус заказа |
| `DELETE` | Удалить | Обычно нет | Удалить товар из корзины |

Важное свойство `GET`: он **ничего не меняет на сервере**. Браузеры, поисковые роботы и кэши исходят из этого и могут повторять `GET`-запросы сами. Ссылка «Удалить», сделанная обычным `GET`, однажды сработает без участия человека.

### Где передаются данные

- В **параметрах адреса** после `?` — для `GET`: фильтры, поиск, номер страницы. Видны в адресной строке и в журналах сервера, поэтому секретам там не место.
- В **теле** — для `POST`, `PUT`, `PATCH`. Формат тела называет заголовок `Content-Type`.

| `Content-Type` | Формат тела | Кто так отправляет |
|---|---|---|
| `application/x-www-form-urlencoded` | `name=anna&age=30` | Обычная HTML-форма |
| `multipart/form-data` | Части с границами | Форма с файлами |
| `application/json` | `{"name": "anna"}` | `fetch` и API |

## Ответ

```text
HTTP/1.1 201 Created
Content-Type: application/json
Set-Cookie: session=abc123

{"id": 17, "product": 4, "qty": 2}
```

Первая строка — код состояния. По первой цифре сразу понятно, что произошло.

| Коды | Смысл | Частые |
|---|---|---|
| `2xx` | Успех | `200` OK, `201` создано, `204` успех без тела |
| `3xx` | Перенаправление | `301` навсегда, `302` временно, `304` не изменилось |
| `4xx` | Ошибка **в запросе** | `400` неверный запрос, `401` не вошёл, `403` нет прав, `404` не найдено, `422` данные не прошли проверку |
| `5xx` | Ошибка **на сервере** | `500` сломался код, `502`, `503` недоступен |

Различие между `4xx` и `5xx` — практическое. `4xx`: неправ тот, кто спрашивал, повторять тот же запрос бессмысленно. `5xx`: неправ сервер, запрос был нормальным и позже может пройти.

`401` и `403` часто путают. `401` — «я не знаю, кто ты, войди». `403` — «я знаю, кто ты, и тебе сюда нельзя».

## HTTP ничего не помнит

Каждый запрос для сервера — с чистого листа. Он не знает, что минуту назад ты вошёл в систему. Чтобы сервер тебя узнавал, браузер прикладывает к каждому запросу **cookie** — небольшую строку, которую сервер выдал раньше заголовком `Set-Cookie`. На этом построены сессии и вход; подробно — в блоке про PHP.

## Посмотреть своими глазами

Открой инструменты разработчика (F12), вкладку **Network**, и обнови любую страницу. Каждая строка — один запрос. Щелчок по строке показывает метод, код состояния, заголовки, тело запроса и тело ответа.

Это первое место, куда нужно смотреть, когда «данные не приходят»: сразу видно, ушёл ли запрос, с чем он ушёл и что вернулось.

## JSON

Формат, в котором API обмениваются данными, — текст, похожий на запись объекта JavaScript. Отличия: ключи и строки только в двойных кавычках, нет `undefined`, функций и комментариев, нет запятой после последнего элемента.

```js
JSON.stringify({ id: 1, tags: ['a'] });    // '{"id":1,"tags":["a"]}'
JSON.parse('{"id":1}');                    // { id: 1 }
```
